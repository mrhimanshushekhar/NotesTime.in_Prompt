  1. HEADING HIERARCHY RULES (CRITICAL)
================================================================================

Headings MUST follow a strict hierarchical order. No skipping levels is allowed.

  <h2> → Main Topic Title (Only ONE per page)
    <h3> → Major Sections (Use multiple)
      <h4> → Subsections (Within each h3 section)
        <h5> → Detailed Concepts (Within each h4)
          <h6> → Advanced Notes, Tips, Warnings (Within each h5)

Violations Not Permitted:
- Skipping from <h2> directly to <h4> without <h3>
- Using <h3> directly under another <h3> without <h4>
- Using <h5> without a preceding <h4>
- Using multiple <h1> tags
- Using <h1> for topics (reserved for page titles only)

Example of Correct Hierarchy (for a mobile security topic):

  <h2>Understanding Mobile Application Security</h2>

    <h3>1. Core Security Principles</h3>
    
        <h4>1.1 The CIA Triad</h4>

  2. CONTENT REQUIREMENTS
================================================================================

2.1 Writing Style Guidelines

Write in simple, human-friendly language that is accessible to beginners while
still providing depth for experienced developers.

Language Rules:
- Use short sentences (15-20 words maximum)
- Break complex ideas into smaller, digestible chunks
- Define technical terms when first introduced
- Use analogies and real-world comparisons
- Avoid jargon unless explained
- Use active voice (prefer "The application encrypts data" over "Data is encrypted
  by the application")

Explanatory Requirements:
- Beginner Level: Provide foundational understanding with basic examples.
  Assume the reader knows nothing about the topic.
- Intermediate Level: Build on the basics with practical implementation details,
  platform-specific considerations, and common patterns.
- Advanced Level: Cover edge cases, performance implications, security trade-offs,
  and complex scenarios.
- Supreme Level: Explore architectural decisions, enterprise considerations,
  future trends, and deep integration strategies.

2.2 Content Elements

Every tutorial must include these sections (in this order):

a. Introduction / Overview (h2 + h3)
   - Clear statement of what the tutorial covers
   - Why this topic matters
   - Real-world context

b. What You Will Learn (h4 inside a card)
   - Bulleted list of learning objectives
   - Use badges for numbering

c. Main Concepts (multiple h3 sections)
   - In-depth explanations with examples
   - Comparisons (tables) where applicable
   - Code demonstrations
   - Diagrams (ASCII art) for complex relationships

d. Practical Use Cases
   - At least 3 use cases with:
     - Use Case Name
     - Problem Statement
     - Solution Approach
     - Implementation Steps
     - Expected Outcome

e. Troubleshooting (h3 with accordion)
   - At least 3 common issues
   - Each issue:
     - Problem Description (h5 text-danger)
     - Solutions (h5 text-success)
     - Step-by-step guidance
     - Code examples where applicable

f. Best Practices (h3 with list groups)
   - At least 5 best practices
   - Each includes: Practice Name (h5), Explanation (p), Implementation Tips
   - Use two-column cards for better visualization

g. Security Considerations (h3 with alert-danger)
   - Dedicated security alert section
   - Specific vulnerabilities and their fixes
   - Actionable recommendations

h. Self-Assessment Questions (h3 with bg-light card)
   - At least 10 questions
   - Ordered list
   - Covers all major topics

i. Summary and Key Takeaways (h3 with bg-light card)
   - Bulleted summary of what was learned
   - Final recommendation (alert-success)

j. Next Steps (h3 with card)
   - Links or references to further learning
   - Practical advice for continued development

2.3 Content Length Requirements

Minimum: 1,500 words total (compulsory)
Recommended Distribution:
- Introduction & Overview: 150-200 words
- Main Concepts: 800-1,200 words
- Subsection Details: 300-500 words
- Troubleshooting & Best Practices: 200-300 words

Typical Target: 1,800-3,000 words

2.4 Real-World Examples Requirement

Every major concept must be accompanied by a real-world example.
Use scenarios like:

  4. CODE BLOCK REQUIREMENTS
================================================================================

4.1 Mandatory Wrapper

NEVER use only <pre> tags. ALWAYS use the following pattern:

  @verbatim
  <pre><code class="language-[language]">
  code content here
  </code></pre>
  @endverbatim

4.2 Supported Languages

+------------------+---------------------+
| Language         | Class Name          |
+------------------+---------------------+
| Bash/Shell       | language-bash       |
| Python           | language-python     |
| PHP              | language-php        |
| HTML             | language-html       |
| JSON             | language-json       |
| YAML             | language-yaml       |
| JavaScript       | language-javascript |
| SQL              | language-sql        |
| Java             | language-java       |
| Swift            | language-swift      |
| Kotlin           | language-kotlin     |
| XML              | language-xml        |
| Groovy           | language-groovy     |
| C                | language-c          |
| C++              | language-cpp        |
| CSS              | language-css        |
+------------------+---------------------+

4.3 Code Block Standards

Every code block must include:
- A brief comment (in the code) explaining what the code does
- Appropriate comments within the code for clarity
- Proper indentation and formatting
- Variable names that are descriptive and meaningful
- Error handling where appropriate

Example (Java):

  @verbatim
  <pre><code class="language-java">
  // This method securely encrypts user data before storage
  public byte[] encryptData(String plainText, SecretKey key) {
      try {
          Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
          cipher.init(Cipher.ENCRYPT_MODE, key);
          // Generate initialization vector
          byte[] iv = cipher.getIV();
          // Encrypt the data
          byte[] encrypted = cipher.doFinal(plainText.getBytes());
          // Combine IV and encrypted data for storage
          ByteArrayOutputStream baos = new ByteArrayOutputStream();
          baos.write(iv);
          baos.write(encrypted);
          return baos.toByteArray();
      } catch (Exception e) {
          // Log error and handle appropriately
          return null;
      }
  }
  </code></pre>
  @endverbatim

  5. HTML FORMATTING RULES
================================================================================

5.1 Indentation Standards

- Use 4 spaces for indentation (no tabs)
- Opening and closing tags must align vertically
- Nested elements must be indented
- Keep attributes on the same line or align them vertically

Correct:

  <div class="card mb-4">
      <div class="card-header bg-primary text-white">
          <h5 class="mb-0">Card Title</h5>
      </div>
      <div class="card-body">
          <p>Content with proper indentation.</p>
          <ul>
              <li>List item one</li>
              <li>List item two</li>
          </ul>
      </div>
  </div>

Incorrect:

  <div class="card mb-4">
  <div class="card-header bg-primary text-white">
  <h5 class="mb-0">Card Title</h5>
  </div>
  <div class="card-body">
  <p>Bad indentation.</p>
  </div>
  </div>

5.2 Tag Alignment

Correct:

  <div class="container">
      <div class="row">
          <div class="col-md-6">
              <p>Content</p>
          </div>
      </div>
  </div>

Incorrect:

  <div class="container">
      <div class="row">
  <div class="col-md-6">
  <p>Content</p>
  </div>
      </div>
  </div>

5.3 Spacing Rules

- ONE blank line between major sections
- NO blank lines between related elements
- ONE space between attributes
- NO trailing spaces on lines

  7. LIST REQUIREMENTS
================================================================================

7.1 Ordered Lists (ol)

Use for:
- Step-by-step instructions
- Sequential processes
- Ranking or ordering information

Example:

  <ol>
      <li>Step one description</li>
      <li>Step two description</li>
      <li>Step three description</li>
  </ol>

7.2 Unordered Lists (ul)

Use for:
- Points, features, or characteristics
- Non-sequential information
- Bullet point explanations

Example:

  <ul>
      <li>Key point one</li>
      <li>Key point two</li>
      <li>Key point three</li>
  </ul>

7.3 List Groups (Bootstrap)

Use for important points or summaries:

  <div class="list-group">
      <div class="list-group-item">
          <h5 class="fw-bold">Item Title</h5>
          <p class="mb-0">Detailed explanation of the item.</p>
      </div>
      <div class="list-group-item">
          <h5 class="fw-bold">Another Item</h5>

      </div>
  </div>
